# BeagleY-AI IMX708 R1 qualification — 2026-08-21

This checkpoint records the hardware state qualified on BeagleY-AI / AM67A (J722S) with an Arducam B0310 / Sony IMX708 on CSI0.

It is intentionally a bring-up checkpoint, not final production image-quality tuning. The sensor, CSI2RX, VPAC/VISS, Wave5 encoder, and OpenHD transport are working. Native IMX708 TI 2A registration and tuned DCC remain future work.

## Platform

- Board: BeagleY-AI / TI AM67A (J722S)
- Running kernel during qualification: `6.12.49-vendor-k3-beagle`
- Camera: Arducam B0310 / Sony IMX708, M12/manual focus
- Port: CSI0
- I2C: `0x1a` on `main_i2c2`
- Input clock: 24 MHz
- CSI lanes: 2
- Link frequency: 450 MHz
- Raw format: SRGGB10 / V4L2 `RG10`
- GStreamer 1.24 capture caps: `rggb10le`

## Qualified raw capture modes

### 2304x1296p56

The 2x2-binned 2304x1296 mode was configured with `vertical_blanking=40`.

Observed qualification result for 560 frames:

- sustained rate: approximately 56.02 fps
- elapsed time: approximately 10.41 s
- no new kernel errors

This is the primary OpenHD mode.

### 1536x864p120

The 1536x864 mode was also configured with `vertical_blanking=40`.

Observed qualification result for 1200 frames:

- sustained rate: approximately 120.12 fps
- elapsed time: approximately 10.39 s
- no new kernel errors

This mode is raw-qualified only; the current DCC profile is pinned to 2304x1296.

## VPAC/VISS qualification

The qualified VISS pipeline is:

```
IMX708 RAW10 2304x1296p56
  -> CSI0 / Cadence CSI2RX / TI CSI2RX
  -> v4l2src io-mode=dmabuf-import
  -> video/x-bayer rggb10le
  -> caps metadata bridge to TI legacy rggb10
  -> tiovxisp / VPAC VISS
  -> NV12 2304x1296p56
```

The Noble/GStreamer 1.24 runtime required a small `libgsttiovx-1.0` compatibility rebuild so `rggb10le` maps to the same 16-bit TIOVX raw container as legacy `rggb10`. The qualified TI `libgsttiovx.so` plugin remains byte-for-byte unchanged.

The isolated runtime published by the qualified installer is:

```
/opt/ti-k3/runtime/releases/ti-11.02.01-j722s-r73341-imx708-raw10le-core-r1
```

A 560-frame VISS smoke test reached PLAYING and normal EOS at the expected source rate. TIOVX teardown reported matching allocation/free counts (`27` / `27`) and no new kernel errors.

A one-frame NV12 capture produced exactly:

- size: `4,478,976` bytes (`2304 * 1296 * 1.5`)
- SHA256 observed during qualification: `864d6db1205d4072f6c5fe238c64f3fc39b3734f99f416500a430405a6ff95ad`

## DCC compatibility state

The current bring-up DCC is generated specifically for IMX708 2304x1296 RAW10, but is assigned compatibility DCC ID `219` because the pinned J722S TI sensor registry does not yet expose native IMX708.

Current contract:

- `sensor-name=SENSOR_SONY_IMX219_RPI` is used only to satisfy the TI registry lookup
- VISS DCC: `/opt/imaging/imx708/linear/dcc_viss_2304x1296.bin`
- 2A DCC: `/opt/imaging/imx708/linear/dcc_2a_2304x1296.bin`
- `format-msb=9`
- AE disabled
- AWB disabled

Do not enable TI automatic AE while using the IMX219 compatibility sensor name. The plugin contains IMX219-specific exposure mapping based on the IMX219 1080p30 timing model, which is incorrect for IMX708 2304x1296p56.

The DCC files are generated by `scripts/build-imx708-default-dcc.sh` from TI imaging ref `REL.PSDK.ANALYTICS.11.02.01.02`. They are intentionally described as default/untuned bring-up DCC.

## Wave5 qualification

Standalone hardware H.264 encoding was qualified at the full VISS output mode:

```
NV12 2304x1296p56
  -> v4l2h264enc / Wave5
  -> H.264 byte-stream, AU aligned
```

The live camera -> VISS -> Wave5 test ran 560 frames to normal EOS in approximately 10.46 s and produced a valid H.264 elementary stream. The stream subsequently decoded successfully through the Wave5 decoder.

A decoder-side CMA warning was observed during one decode test when `vdec` requested a contiguous 32 MiB block. It did not affect the air-side encoder path and decoding still completed.

## OpenHD transport checkpoint

The matching OpenHD consumer checkpoint is on branch `imx708-r1-20260821` in `ILAMtitan/openhd-k3-integration`.

The native OpenHD path is:

```
IMX708 RAW10 2304x1296p56
  -> VPAC/VISS NV12
  -> queue depth 1, leaky downstream
  -> Wave5 H.264
  -> h264parse
  -> RTP mtu 1024
  -> OpenHD wifibroadcast
```

At MCS2 / 20 MHz, OpenHD calculated approximately 11 Mbit/s maximum video rate. A fixed 12 Mbit/s Wave5 stream caused heavy RF-delivered corruption because the current TI path does not yet support OpenHD dynamic bitrate updates.

Reducing the camera setting to **6 Mbit/s** removed the corruption. Keep 6 Mbit/s as the known-clean R1 transport default until dynamic Wave5 bitrate control is implemented and retested.

## Current manual image-quality baseline

Because AE/AWB are disabled, indoor exposure was manually evaluated while OpenHD was streaming.

Known-good indoor starting point:

- `exposure=1280` (maximum for this 56 fps timing is 1288)
- `analogue_gain=512`
- `digital_gain=256` (unity)

Color is generally reasonable with the default DCC. A green tint appears primarily when fluorescent fixtures are directly in frame and highlights are overexposed/clipped. This is treated as an exposure/highlight/DCC-tuning issue, not a Bayer-order failure. Manual white-balance offsets are not part of the locked R1 baseline.

These manual exposure values are a bring-up preset, not a production outdoor default.
